# 日本語ドキュメント作成

読者が文書を使って判断・操作できる状態まで仕上げる。ユーザーの指定、対象リポジトリの執筆規約、既存文書の文体を優先する。

## 1. 文書の目的を定める

- 新規作成、既存文書の更新、推敲、指摘のみのどれかを判定する。指摘だけを求められた場合は本文を編集しない。
- 対象読者、読了後にできること、対象範囲、出力先を依頼と既存ファイルから把握する。指定がなければ日本語の Markdown とし、配置はリポジトリの慣例に合わせる。
- 不明点が文書の内容を大きく変える場合だけ質問する。軽微な不足は仮定を短く示して進める。短い文書のために構成案の承認待ちを挟まない。
- 推敲では意味、確度、数値、条件、引用、識別子を保つ。内容の誤りも修正する依頼か、表現だけを整える依頼かを区別する。

## 2. 根拠を集める

- 指定資料と既存文書を読み、実装の説明なら関連するコード、設定、テスト、利用例を確認する。文書間の矛盾は原典や実装に戻って調べる。
- 現在の動作、将来の設計案、推測、未決定事項を区別する。設計案を実装済みの仕様として書かない。
- 数値、対応バージョン、制限、コマンド、API 名の根拠を確認する。読めない資料や未確認の動作を推測で埋めない。
- 根拠が足りない箇所は、草稿なら確認事項を明示し、完成稿なら確認するか主張を狭める。完成を妨げる未確認事項は報告する。
- 外部資料に基づく主張には近くに出典を置く。引用と自身の説明を分け、文書に不要な引用やリンクを増やさない。

## 3. 読者の作業に合わせて構成する

文書の種類に応じて、次の要素から必要なものを選ぶ。見出しを埋めるために空の節を作らない。

| 文書 | 優先する内容 |
| --- | --- |
| README | 何ができるか、前提、最小の実行例、結果の確認、詳細へのリンク |
| 設計書・仕様書 | 解決する問題、対象範囲、制約、仕様や決定、理由、影響、未決定事項 |
| 操作・運用手順書 | 開始条件、実行場所、順序、期待結果、失敗時の対応、必要なら復旧手順 |
| 技術記事・解説文 | 読者の疑問、理解に必要な概念、説明と例、適用条件 |
| 報告書 | 確認できた結果、根拠、影響、未解決事項、必要な判断や次の作業 |

概要で用途や結果を示し、本文で必要な根拠や操作を説明する。見出しは読者が探す対象や疑問を表すものにする。既存文書の更新は関連箇所に絞り、リンク先や目次への影響も確認する。

## 4. 本文を書く

- 段落ごとに話題を絞り、最初の文で対象を示す。説明を追うために必要な定義を先に置く。
- 誰が何をするのかを明記する。手順では作業ディレクトリ、入力、期待結果を対応させ、サンプル値と実際の値を区別する。
- 原因を説明する場合は、結果に至る理由と条件を書く。一例からすべてのケースに成立する結論を出さない。
- 用語、単位、表記、文体をそろえる。日本語の説明では、一般語や慣用的な訳語のある技術用語を英語のまま挿入せず、自然な日本語または定着したカタカナ表記で書く。説明に必要なファイル名・API 名は正確に残す。
- 順序のある操作には番号付きリスト、並列項目には箇条書き、比較には表を使う。通常の説明は段落でつなぐ。
- 図やコードには、何を確認するための例かを添える。複数の例を同じものとして参照する場合は条件とデータをそろえる。

## 5. 内容と表現を推敲する

まず仕様との矛盾、論理の飛躍、条件の欠落を直し、その後に文体を整える。

- 主張の強さを根拠に合わせる。推定を事実に変えたり、保証できない結果を約束したりしない。
- 各段落が読者に何を追加しているか確認する。重複する説明を削る際も、操作に必要な前提と例外は残す。
- 強調や抽象語だけで済ませた箇所を、対象・操作・結果で説明し直す。説明できなければ追加確認か削除を選ぶ。
- 不自然な直訳、過剰な比喩、装飾的な前置きを見直す。具体例が必要なら [推敲例](references/revision-examples.md) を読む。
- 英単語が日本語の文中に不用意に残っていないかを、追加の指摘を待たずに確認する。本文だけでなく見出し、表、箇条書き、図の説明、リンクの表示名も対象にする。判断例は [推敲例](references/revision-examples.md) の「文章中に残った英語を整える」を読む。
- 一般語は日本語に、技術用語は対象分野で定着した訳語やカタカナ表記に整える。英語の複合語やスラッシュで連ねた語は、関係や操作を確認して文ごと書き直す。単純なカタカナ化で意味を曖昧にしない。
- 正式名称、識別子、パス、コマンド、設定値、原文の引用、API・HTTP などの定着した略語は原綴りを保つ。専門用語であることだけを理由に英語表記を残さない。訳語だけでは意味が特定できない場合は初出に短い説明と原語を添え、以降の表記をそろえる。
- 単語の出現だけで誤りと判定しない。専門用語の概念と原文の確度を保ち、自然な「難しいです」などの表現も一律に禁止しない。
- 更新で不要になった参照、古い例、節どうしの食い違いを確認する。

## 6. 成果物を確認する

- 見出し階層、リンク先、表、コードフェンスを確認する。見出しを日本語化した場合は、その見出しを指す目次・文書内外のアンカーも確認して更新する。利用可能なら既存の文書ビルドと lint を実行する。
- 仕上げに対象文書の英字を検索し、残した英語が正式名称・識別子・定着した略語などに該当するか文脈で確認する。例として `rg -n '[A-Za-z]+' -- docs/target.md` で候補を拾えるが、検索結果を一律に置換しない。インラインコードで囲まれていても一般概念の説明なら見直し、実際の識別子なら維持する。この確認は textlint の指摘の有無によらず行う。
- コマンド例は実行環境と副作用を調べ、安全に実行できる範囲で検証する。検証していない操作を成功済みと書かない。
- textlint が既に導入されている場合は、既存設定で変更した文書を検査する。導入・設定・検出結果の扱いは [textlint の利用手順](references/textlint.md) を読む。
- textlint がなければ目視による推敲を完了する。文書作成だけの依頼に合わせて依存関係や hooks を追加しない。導入も依頼されていれば設定まで実施する。
- 検出件数ゼロを文章品質や事実の正しさの保証にしない。機械検査後も意味と読者の作業を確認する。

## 7. 引き渡す

依頼された完成稿、編集済みファイル、または指摘を返す。ファイルを編集した場合は場所、変更の要点、実施した検証、残る確認事項を簡潔に示す。本文だけを求められた場合は作業報告を混ぜない。
