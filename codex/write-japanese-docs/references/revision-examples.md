# 意味を保つ推敲例

以下はこのスキルのために作成した例であり、参考資料からの引用ではない。修正文の事実が資料で確認できる場合にのみ採用する。例文の数値や条件を実際の文書に流用しない。

## 操作と結果を明らかにする

修正前:

> この機能は文書管理を飛躍的に進化させる強力な基盤です。

資料で確認できた機能が「文書ごとに承認者を設定できる」なら、次のように書く。

> 文書ごとに承認者を設定できます。

根拠のない評価語を別の評価語に置換せず、確認できる動作を書く。具体的な効果まで資料になければ、所要時間の削減などを付け足さない。

## 不確実性と条件を残す

修正前:

> ログを見る限り、同時更新が原因かもしれないと考えられます。

修正後:

> ログからは、同時更新が原因の可能性があります。

調査中であれば「同時更新が原因です」に変えない。追加で調べる対象が分かっている場合は、その確認方法を続ける。

仕様が「最長 24 時間以内の再送に限って重複を除外する」なら、「重複を防ぎます」と短縮せず、期間の条件を残す。

## 手順を再現できるようにする

修正前:

> 適切に設定してから実行し、問題がないことを確認します。

設定ファイル、実行コマンド、期待結果が確認できた場合は、次の情報を順に書く。

1. 編集するファイルと設定項目、値の選び方。
2. コマンドを実行するディレクトリとコマンド。
3. 成功時に確認する表示や生成ファイル。
4. 想定する失敗と対処方法。

未確認のコマンドを補完して実行例にしない。文法を説明するコードと、そのまま実行できるコードを区別する。

## 語彙チェックを文脈で判断する

| 文 | 判断 |
| --- | --- |
| 「この施策が効きます」 | 何がどう変わるかを資料から確かめ、効果を具体的に書く。 |
| 「検査工程で部品の寸法を測定する」 | 製造の文書なら対象と操作が明確なので維持する。 |
| 「照合 API の `match_id` を指定する」 | 正式名称と識別子なら維持する。 |
| 「重要な課題を包括的に解決します」 | 解決する課題と対応範囲を明記する。分からなければ断言を削る。 |

検出語を別の曖昧な語に変えても、説明の不足は解消しない。元の語を残すほうが正確なら残す。
